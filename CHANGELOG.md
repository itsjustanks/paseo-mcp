# Changelog

## 0.15.0 — 2026-09-26

The surface explains itself to someone who has never heard of MCP. **Copy to all my AI apps** copies every server to every AI app and account that lacks it, after a preview. The Servers tab is a gallery of the servers you have, and the Add gallery shows only what you don't have yet. The Add gallery and the sign-in read no longer wait on a busy daemon (`paseo-mcp.auth took 10.0 s`, `paseo-mcp.catalog took 5.7 s` on paseo-ankit).

Add a server once here, and every AI app on this computer can use it." **Learn more** opens four short paragraphs: what a server is, web servers versus ones that run on this computer, signing in, and why fewer servers keep assistants quick. The words live in `shared/overview.ts` (`MCP_EXPLAINER`, `MCP_LEARN_MORE`).
- The rows read plainly: "AI apps · 4 servers missing from some apps" (was "Editors · 3 gaps · 1 of 4 editors hold all 6 servers"), "Projects · 3 projects have their own servers" (was "3 with .mcp.json"), "Paseo tools · on · 61 tools · for all 6 AI apps" (was "for 6 of 6 providers"), "Health · 1 not working", "Sign-in · all signed in".

### Copy to all my AI apps (replaces Sync accounts)
- Every user-level server goes into every AI app and account on this host that doesn't have it: across apps (Claude → Codex and Kimi, Codex → Claude) and between accounts of one app. It copies servers only: Claude project trust is not touched (Sync accounts still copies it, now safely; see Fixed).
- **Only what can be copied exactly.** Between two accounts of one app, the entry goes as it is. Between apps, only the settings every app shares. Anything else is skipped with a plain reason, in the preview and the result: a server switched off (Codex `enabled = false`, Claude's `disabledMcpServers`), one with an app-only setting ("copy this one by hand: it uses a Codex-only setting (enabled_tools)"; `bearer_token_env_var`, `env_http_headers`, `startup_timeout_sec`, a `tools.<tool>` table …), a value over several lines, an `sse` connection, and a `${VAR}` the other app wouldn't fill in. Into Codex, a Claude header `Authorization: Bearer ${X}` becomes `bearer_token_env_var = "X"` and a header whose whole value is `${X}` goes in `env_http_headers` (Codex's own keys, developers.openai.com/codex/mcp); mixed text with `${…}` is skipped, and so is any `${…}` for Kimi or Grok.
- **Preview first.** One row per server: which apps and accounts will get it ("Adds it to Codex (demo@example.com), Claude (work@example.com) and Kimi"), which copy is used ("from Claude (demo@example.com)", the first JSON config that has it, as "Add to missing" picks), "includes its saved key" when the copy carries a header, env value or key in its address or arguments, and a note when the apps that have it hold different versions. A tick box per server, on by default, leaves one out. Then **Copy N servers**, with how many places change.
- **How it writes.** Through the same writers as "Add to missing", grouped by file: every server for one file goes in ONE write, after ONE backup (so the backup is always the file as it was), atomically, in the file's own format with the target app's header table (Codex `http_headers`, Grok `headers`). Each server is then read back, header table included; one that doesn't match is reported, with its backup beside it.
- **Never removes, never overwrites.** Who has a server is decided by NAME, in any form the file writes it (`[mcp_servers.x]`, an inline `x = { … }`, a dotted key), never by whether this app could read it. The plan is worked out again from the files, and the provider settings read fresh, when you press Copy; and the write itself re-reads the file and refuses a name it has ("already has a server called jam"). A place that has one is skipped: "it already has it", or "it already has a different server called jam; left as it is".
- **The result**, per server and per app: "Copied to Codex and Kimi", "Not copied to Kimi: …". A file that won't parse is left alone and reported; the rest are still written.
- **Left out:** Paseo's own server (named `paseo`, or at `/mcp/agents`: the daemon adds it to agents itself) and project `.mcp.json` servers (only user-level configs are read).
- **Where:** a card on Overview ("Use your servers in every AI app", with the explainer "Add a server once, and this copies it to every AI app and account on this computer that doesn't have it yet. Nothing is removed or replaced. A server that only one app understands is left for you to copy by hand. Sign-ins aren't copied: each app signs in on its own."), the gaps next step, and a line with the button on the Servers tab's **Missing from some apps** filter.
- `paseo-mcp.sync` still answers as before for an older app; this app no longer calls it.

### Faster on a busy daemon
- **Why it waited.** `handleMcpAuth` awaited `discoverProjects` (the daemon's `projects.list`), and `handleMcpCatalog` awaited it and then `buildDestinations`, whose provider settings come from `config.get`, one after the other. Each call is allowed 10 s (`withDeadline`), and a busy daemon took most of it on every read: the 10.0 s in the log is that deadline.
- **One cache for both** (`server/daemon-cache.ts`, `daemonRead`). A read answers from the last copy at once; a copy older than 15 s is refreshed in the background and the read still doesn't wait (the 0.11.3 pattern). One call is in flight at a time, whoever asks. A failed call keeps the last good copy and isn't tried again from a read for 15 s. With no copy yet, the first read waits, as before, and a failure is handled as before: `discoverProjects` falls back to the folder scan, and the provider settings read fails the call.
- **Writes and Refresh.** Every write (Copy, Add, Add to missing, Remove, Rename, edit, the JSON editor, import, the per-workspace switch) reads the provider settings fresh (`buildDestinations(paseo, { fresh: true })`), so an app switched off in Paseo a moment ago is never written to; the cached copy is for display. Changing Paseo's tool settings from the Servers tab throws the copy out (`invalidateDaemonReads("config")`): the very next read waits for the new answer instead of returning the old one. A call that was already running when the write started is never taken as fresh, and never overwrites a newer answer. **Refresh everything** in the Add gallery (`refresh: "all"`) and **Refresh** on sign-in (`refresh: true`) re-read in the background and join a call already running (`refreshDaemonReads`). Adding a server to a project that isn't in the copy reads the list again, waiting this once, so a project registered seconds ago is found. The plugin writes nothing that changes Paseo's list of projects; a project's `.mcp.json` is read from disk on every call, as before.
- **Together.** The gallery now asks for the project list and the provider settings at the same time, so its first read on a cold, slow daemon waits once (8 s in the test), not twice (16 s).
- Health, tools, the per-workspace switches and every other caller of `discoverProjects` and `buildDestinations` share the same copy.

### Fixed (also affected earlier releases)
Old bugs in the shared writers behind **Sync accounts** and **Add to missing** (live since 0.12.0 and earlier), which Copy to all my AI apps would have repeated across every app at once:
- **Sync overwrote a second account's project settings.** For every project the main Claude account trusted, Sync replaced the other account's allowed tools, project servers and `.mcp.json` choices (`allowedTools`, `mcpServers`, `enabledMcpjsonServers`, `disabledMcpjsonServers`) with the main account's, even an empty list. It now copies only "trusted" and the onboarding flag, and only where that account doesn't have them yet; an account's own answer, even "not trusted", stays.
- **Codex values over several lines were cut to their first line.** A list like `enabled_tools = [` across lines was carried as that one line, which made the file it was copied into unreadable (Sync, Add to missing, Rename). Such a server is now left for you to copy by hand, with the reason. Every TOML write is checked as a whole file afterwards (each table once, quotes and brackets closed, no list left open, no server both inline and as a table); a write that fails the check is put back from its backup and reported. A file that already fails the check isn't written.
- **Servers written inline or with a comment were counted as missing.** `foo = { url = … }` under `[mcp_servers]`, or `url = "…" # note`, read as "not there", so a second `foo` was added and Codex refused the whole file. Presence is now by name, and add-only writes refuse a name the file already has in any form. Values with a comment after them now read correctly.
- **Settings crossed between apps.** Add to missing and Copy carried Codex-only lines (`enabled = false`, `bearer_token_env_var`, `enabled_tools` …) into Grok and wrote headers under Codex's table name into Grok; subtables such as `env_http_headers` and `tools.<tool>` were dropped on every rewrite. Each app now gets its own header table, other apps never get Codex's lines, and unknown subtables are kept.
- **Also:** one press wrote a file once per server, so 20+ servers pruned the pre-change backup away (now one write and one backup per file); "includes its saved key" missed a user name or password in an address, a token-like path, `--pat`/`-k` values and bare `ghp_`/`sk-`/`xox…`/`eyJ…` keys (the list's detail line hides them too); writes could use provider settings up to 15 s old.

## 0.14.1 — 2026-09-25

The chip, the context meter and the budget warning now read tool search right on a gateway that keeps it on with `ENABLE_TOOL_SEARCH="force"`.

### Fixed
- A managed `ENABLE_TOOL_SEARCH="force"` counts as tool search on, through a custom `ANTHROPIC_BASE_URL` and under `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS` (AI Router's routed sessions). It is the value Claude Code 2.1.280 checks for itself (`isToolSearchForceOverride`, first-party connections only). Before, the plugin didn't know the value and said tool search was off. On a fleet that runs with it (`/etc/claude-code/managed-settings.json` = `{"env":{"ENABLE_TOOL_SEARCH":"force"}}`, where routed chats went from 70 tools sent up front to 13), every routed agent's chip showed the full token cost, and the budget warning fired for no reason.
- A managed `"true"` no longer counts as on under the betas flag. Tested on the same fleet, it changed nothing. 0.11.2 had read the docs' "managed settings can keep tool search on" as covering any managed value.
- On a cloud provider (Bedrock, Mantle, Claude Platform on AWS, Agent Platform, Foundry), `force` has no effect, as in Claude Code's own check.

### Tests
Tool-search tests cover `force` under the betas flag, a routed AI Router session and the built-in provider, the managed file on disk, any letter case, and Bedrock; and a managed `true` under the betas flag reading off.

## 0.14.0 — 2026-09-25

The composer chip is now a context meter: "14 MCP · ~38k tokens", what this agent's MCP tool definitions cost, or "14 MCP · deferred" while tool search is on. The agent's MCP panel shows what this chat used and what it loaded without using, and a failed sign-in now shows up in the chat itself.

### Context meter
- **Estimate.** A listed HTTP server is measured: each tool's name, description and input schema as JSON, divided by four, from the raw `tools/list` answer before its descriptions are cut to one line (`definitionTokens` on each tool list). Paseo's built-in tools count 135 tokens each, measured the same way on Paseo 0.9.1's own `tools/list` on 2026-09-24 (61 tools, about 8,250 tokens; 44 to 535 per tool). A server that cannot be listed (stdio, OAuth before sign-in, unreachable) counts a documented default of 2,500: the budget's five tools per server at 500 each, an assumption between Paseo's measured 135 and the roughly 1,500 per tool Anthropic reported for large servers. Servers the agent was created with (0.11.2) are measured from their probe. Servers switched off for the workspace are left out. All of it is in `shared/meter.ts`.
- **Chip.** With the meter in, the count is the servers this agent loads (Paseo's included) and the tail is "~38k tokens", or "deferred" when the provider's tool-search verdict (0.11.0) is on. "2 issues" and "3 need sign-in" still win, as before. Until the meter arrives, or on a host older than 0.14.0, the label is exactly the 0.13 one; the chip never waits for it.
- **Panel.** A **Context** section: the headline ("8 servers · ≈27k tokens of tool definitions"), "This chat: 360k of 1M context; MCP definitions ≈27k of that." with a bar when the agent has reported its context use (`lastUsage`), how many servers are at the default, and **Heaviest servers**, biggest first, each with how it was estimated. Every number says "≈" or "~".

### Used vs loaded
- The host reads the agent's timeline through the plugin API (`paseo.agents.ref(id).timeline.refetch`): the newest 500 items, then older pages, to 2,000 at most, projected, kept a minute per agent, in the background. The panel shows "Used in this chat: supabase ×4, linear ×1", "Loaded but unused: 6" with their names, and says when older items were not read.
- Tool names map to servers in both forms the daemon writes (read in Paseo 0.9.1): Claude's `mcp__<server>__<tool>` (with Claude Code's spelling of a server name, anything outside `[A-Za-z0-9_-]` as `_`) and Codex's `<server>.<tool>` (`buildMcpToolName`). Names are matched against the servers the agent loads, longest first, so `my_server` never splits into `my`.
- **Turn off the unused ones for this workspace**: one button, then a confirm that names exactly the servers that change, says it applies to new sessions, and names any unused server left alone because it has no per-workspace switch for this provider. The host decides and flips each through the existing switch (`paseo-mcp.set-enabled`), one at a time, and reports what changed (see Review fixes). Only servers with a switch (README, Per-workspace switches) that are on now are offered.

### `/mcp`
- A client slash command in every agent's composer that opens that agent's MCP panel, the same way the chip does. Paseo ranks its own commands first, then plugins', then the provider's, so in Paseo's composer `/mcp` now opens this panel and hides the provider's own `/mcp`, which only works interactively in the CLIs anyway. A message with an attachment still reaches the provider.

### Sign-in card in the chat
- New setting **Chat notices: sign-in problems** (Health checks screen, on by default). When an MCP tool call in a chat fails with an auth-shaped error (401 or 403 with an HTTP or status word, "unauthorized", "invalid_token", "needs authentication", "authentication required"), the host appends one plugin timeline item, kind `mcp-sign-in`, data `{ server, provider }` and nothing from the error. The app renders it as a small card, "linear needs sign-in", with **Connect**, which opens the agent's MCP panel with that server's sign-in rows first: the same OAuth flow as its row.
- Detected on `agent.turn_ended`, which carries the turn's timeline, so there is no subscription; only while an app is connected (0.8.0) and the setting is on. A turn with no such failure costs one pass over its items and no read. Panel reads of the chat run the same check, for failures from before an app connected.
- At most one card per server per chat: the first time a chat is seen, its timeline is read back for cards an earlier run added; if that read fails, nothing is appended. A server is marked before its append and a failed append is not retried. Each card's id is `mcp-sign-in:<server>`. Paseo's own server never gets one.

### Review fixes
"Turn off the unused ones" must never switch off a server this chat used; when in doubt a server counts as used.
- **The host decides.** New RPC `paseo-mcp.turn-off-unused` (`{ workspaceId, providerId, agentId, expected }`). On confirm the panel sends the list it showed, not a series of switches. The host reads the server list and the whole chat again, uncached, rebuilds the plan, and flips the servers through the `set-enabled` path only when its plan is exactly `expected`. Otherwise it switches nothing: "The chat changed since you reviewed this list; review again", with the new plan. A read that stops at the 2,000-item cap ("This chat is too long to be sure which servers it used") or has a failed page ("Couldn't read this chat's history") also switches nothing. Before, a chat longer than the cap could switch off a server used only in its older part.
- **The panel says when it can't be sure.** `agent-chat` returns `chat.complete` (every page read), and `stale` with `failedAt` when it serves an earlier read after a failed one. The action shows only for a complete, fresh read; otherwise a plain line says why.
- **No known servers, no verdict.** If the meter's server list failed, the chat read now fails too, instead of counting every call against an empty list. And a call to a server outside the known list counts as a use of every loaded server it could belong to: the same name, Claude's `_`-for-`.` spelling, or either name a prefix of the other (`mcp__ikit_attio__…` and Codex's `ikit.attio.search_records` both keep `ikit.attio`). "Loaded but unused" follows the same rule.
- **Sign-in cards only for known servers.** A failed call to a server this agent was not started with no longer gets a card. The turn check now works out the known list first.
- **Ambiguous tool names.** When more than one known server could own a name (`github` with a tool `enterprise__login`, and `github__enterprise`), the call counts as used by all of them and gets no card.
- **The chip never probes.** The meter path passes `probe: false` to the agent-servers read: cached tool counts only, no `tools/list` to an added server or to Paseo's own endpoint, and no `codex mcp list` for a Codex agent. The panel's own read still refreshes them.

## 0.13.0 — 2026-09-24

The gallery reads **libraries**: lists of MCP servers you subscribe to by address or by file, in the official MCP Registry's list shape. The 0.12.0 team catalogue is now one of them, and the MCP Registry search is another, off by default.

### Libraries
- A library is JSON in the MCP Registry's list shape, `{ "servers": [ { "server": <server.json>, "_meta": … } ], "metadata": { "count" } }`, each `server` a [server.json](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/server-json/generic-server-json.md) (schema `2025-12-11`: `remotes` with `streamable-http` or `sse`, `headers` as `{ name, value, variables, isRequired, isSecret }`; or `packages`). Optional curation sits in `_meta["io.github.itsjustanks/mcp-gallery"]`: `id`, `displayName`, `category`, `publisher`, `iconUrl`, `auth` (`oauth` | `token` | `none`), `docsUrl`, `verifiedAt`. Each field is read on its own, and a field that doesn't fit is ignored; without curation the card uses server.json's `title`, `websiteUrl`, `repository` and `icons`. A server named only `…/mcp` or `…/server` is called after its publisher (`com.acme/mcp` → `acme`).
- Three kinds, picked from the address (or by hand with **Read as**): an https address ending in `.json` is one document; any other address is a registry, searched through `GET {base}/v0.1/servers?search=…&version=latest&limit=100`, following `metadata.nextCursor` for up to three pages; a path on the host (absolute or `~/`) is a private library that is never hosted. Plain http is read only from `localhost`, `127.0.0.1` or `::1`. An address with a user name, a password or a key in its query is refused.
- Defaults: **MCP Gallery** (`https://raw.githubusercontent.com/itsjustanks/mcp-gallery/main/v0.1/servers.json`), on, and **MCP Registry** (`https://registry.modelcontextprotocol.io`), off. The gallery repository is not published yet; its read says "answered HTTP 404: nothing is published at that address (yet). The recommended servers shipped with the plugin are shown instead."
- **Merging** (as first built; see Review fixes for the rules that shipped). Libraries are read in order and a server name is shown once: the first library to list it wins. A library card at the same endpoint as a Recommended card (address, or package and ecosystem) replaces it, so the library can refresh descriptions, icons and categories without a plugin release; the 31 shipped servers are the offline fallback. A library card is **Official** only when its address is one the Recommended shelf checked; otherwise it is **Library**, "whoever can change that library can change this entry". A library card at another address never hides a Recommended card, even with its id. A registry result already shown by name or address is left out.
- **Rules.** Library text is untrusted. Every server becomes a catalogue entry and passes the team catalogue's rules (`validateEntry`, origin team): https only, no literal key, no `${…}`, no control characters or bidi text, header names without `.`, exact package versions (`npx @acme/mcp@1.4.2`, `uvx acme-mcp==2.0.1`), no runner flags that pick a source, no runtime variables (`NODE_OPTIONS` …). One that fails is refused by name with the reason and the rest still show. A package the plugin doesn't start (an image, `mcpb`, NuGet, a package served over HTTP) is shown with **Add by hand**. Header, env and argument values are `{PLACEHOLDER}` inputs, secret by default; `isSecret: false` makes one public only when its name is on the public list and it is not in a credential position. An icon must be https. A document is capped at 1 MB (declared length, streamed count, and a file's size) and 500 servers; a registry answer at 8 MB per page.
- **Reading.** Every read is in the background; the gallery answers from memory and reads again every 1.5 s while one runs. A document is kept for 15 minutes (the team catalogue was kept an hour), **Refresh** reads it again, and a failed read keeps the last good copy, says why, and waits a minute before it is tried again. Registry searches are kept a day, as before. No library or cache ever holds a stored value.

Its value is write-only as before, now kept per library in `team-auth.json` (`{ "keys": { "<library id>": { value, origin } } }`, 0600), bound to the origin of that library's address and sent only there, never on a redirect. The 0.12.0 store (`{ teamHeaderValue, origin }`) reads as the Team library's key; a moved address still deletes the key and says so.

### Trust (registry facts, read 2026-09-24)
- The registry API is `GET https://registry.modelcontextprotocol.io/v0.1/servers` with `search` ("substring match" on the name), `version` ("'latest' for latest version"), `limit` (default 30, maximum 100), `cursor` (answer's `metadata.nextCursor`) and `updated_since` ([openapi.yaml](https://registry.modelcontextprotocol.io/openapi.yaml)). Each version carries `_meta["io.modelcontextprotocol.registry/official"]` with `status` and `isLatest`.
- Namespaces: "If you choose GitHub-based authentication, your server's name … MUST be of the form `io.github.username/*`"; with DNS or HTTP authentication it "MUST be of the form `com.example.*/*`, where `com.example` is the reverse-DNS form of your domain name" ([registry authentication](https://modelcontextprotocol.io/registry/authentication)). The registry's validators check a remote URL's format and refuse localhost, but do not tie it to the namespace's domain ([`internal/validators/validators.go`](https://github.com/modelcontextprotocol/registry/blob/main/internal/validators/validators.go), `validateRemoteTransport`). So the plugin makes that check itself.
- **Official**: every remote address is one the Recommended shelf already checked against the vendor's docs.
- The publisher's claimed namespace is shown as plain text on the card ("published as supabase.com", "published as github.com/<user>"), not as a badge, with one line: the registry checks that the publisher owns that domain or GitHub account, not who runs the service. There is no tier between Official and Community.
- A registry remote that lists no headers reads **Sign-in unclear** (auth `unknown`), not OAuth: the registry can't tell the two apart.
- **Community**: everything else, with a plain warning: "A third party relays your traffic and any key you give it." for a remote, "Runs code on this server." for a package.
- Examples from the same day, now test fixtures: "supabase" returns `com.supabase/mcp` (`https://mcp.supabase.com/mcp`, Official because it matches the recommended entry), `ai.waystation/supabase` (Community) next to Smithery relays (`ai.smithery/*` on `server.smithery.ai`, Community), `io.github.mcp-dir/supabase-mcp` on `api.mcp.ai` and `io.github.sadri-dridi/*` on a `workers.dev` host (Community). ### Project files and secrets (source read 2026-09-24)
- Claude Code expands environment variables in `.mcp.json`: "`${VAR}`: expands to the value of environment variable `VAR`", "`${VAR:-default}`" likewise, in `command`, `args`, `env`, `url` and `headers`. An unset variable with no default leaves the file loading, with "a missing-variable warning" and "the unexpanded `${VAR}` text as-is" ([MCP docs, environment variable expansion](https://code.claude.com/docs/en/mcp)). The same page says to "Check `.mcp.json` into version control".
- So at project scope a secret input is written as `${VAR}` and the sheet says which variables to set, and where: the environment Claude Code starts with (for Paseo agents, the daemon's environment or the provider's env in Paseo's settings). If one is already set in the daemon's environment the sheet says so, by name only ("MCP_… is already set on this host: this server would receive that value"). No key field is shown at project scope. Inputs are secret by default; only one named on a short list (region, project, workspace, org, team, site, host, port, database, schema, env, locale, timezone, mode and their `_id`/`_name` forms) in a place that allows it is written as typed. As a last guard, a project definition that still carries a typed secret or reads like a key is refused, with a pointer to user level.
- The plugin names every variable itself, capitals, digits and `_` only. A recommended entry's is `MCP_<ID>_<INPUT>` (`MCP_HEROUI_PRO_HEROUI_PERSONAL_TOKEN`; an input that repeats the id is not repeated, so DigitalOcean's is `MCP_DIGITALOCEAN_API_TOKEN`). A team or registry entry's is `MCP_TEAM__<ID>__<HASH6>__<INPUT>` or `MCP_REG__…`, where HASH6 is the first 6 hex of the SHA-256 of its address (or its package with the ecosystem), so it can't land on a recommended entry's variable or another entry's, and `__` (which no part holds) keeps `a-b` + `C` apart from `a` + `B_C`. Nothing in an entry names a variable, and an entry may not hold `${…}` at all, so it cannot pick which of your variables goes to its server.
- In a remote server's `url` and `headers`, Claude Code reads some credential variables as empty: "Claude Code's own credentials, such as `ANTHROPIC_API_KEY`", cloud provider credentials, and others "such as `HTTPS_PROXY` and `NPM_TOKEN`" ([Credential variables that read as empty](https://code.claude.com/docs/en/mcp)). Claude Code also reads some `MCP_` names itself (`MCP_CLIENT_SECRET`, `MCP_TIMEOUT`, `MCP_OAUTH_CALLBACK_PORT` and more, read from Claude Code 2.1.280). One list, `RESERVED_ENV_NAMES` in `shared/catalog.ts`, holds all of these; a generated name that equals or starts with one is refused.
- Codex does not read `.mcp.json`. **Add project servers to agents** passes an entry on as written, with no `${…}` expansion, and by default skips entries carrying credentials; the sheet says so.

### Security (found in review before release)
- An entry may not hold `${…}` anywhere. `Authorization: "Bearer ${UNSET_X:-sk_live_…}"` passed validation and put the key in the project's `.mcp.json` through the fallback; entries now use `{INPUT}` placeholders only, and the plugin alone writes `${VAR}`.
- An input in a credential position (the Authorization header, a header or env named like a credential, any query value, a credential argument) is secret whatever the entry says; a registry `isSecret: false` never wins on a credential name. The preview is built from the planned definition, so it masks exactly the secrets and never shows masked what the file holds as typed.
- Variable names are built by the plugin (`MCP_<SERVER>_<INPUT>`). An entry's `envVar`, input id or registry placeholder used to name the variable, so `X-Trace: {OPENAI_API_KEY}` would have sent your `OPENAI_API_KEY` to its server.
- Copy as catalogue entry fails closed: every query value becomes a placeholder, the fragment is dropped, and an address that does not parse is not copied. A broken `%` escape used to return the original URL, token included.
- Reads are capped as they stream: a declared length over the cap is refused unread, and the body is counted and dropped past 1 MB (team) or 8 MB (registry). A team file is stat-ed first; a directory, FIFO, `/dev/zero` or anything over 1 MB is refused before it is read (a FIFO used to hang the read for good).
- The team source no longer leaks: a JSON error says "not valid JSON (line N)" without quoting the file (pointing it at `~/.env` echoed `"OPENAI_API"…`), the address comes back without its query or user name, and the header value moved out of the settings document (which Paseo sends to every client) into a write-only store. An old value is moved there on first read and cleared from `catalog.json`; the document stays version 1.
- A second review showed five of the fixes above could be sidestepped. Each is now a safe default rather than a longer deny-list:
  - **Secret by default.** An input is public only when its name is on a short allowlist (region, project, workspace, org, team, site, host, port, database, schema, env, locale, timezone, mode and their `_id`/`_name` forms), as the whole name or its last words, and it is not in a header or env line named otherwise. `DATABASE_URL`, `MONGODB_URI`, `SLACK_WEBHOOK_URL` and `X-Access` used to be written into `.mcp.json` as typed. A registry `isSecret: false` makes an input public only when it is also on the list; `isSecret: true` always makes it secret. In a team or registry entry, anything in the address (host and path too) or in any argument is secret: `-k {V}`, `--connection-string {V}` and the Postgres server's bare database address were written as typed. A value, typed or a registry default, that reads like a credential (`scheme://user:pass@`, `sk-`, `sk_`, `ghp_`, `gho_`, `xox`, `eyJ`, a Slack webhook) is secret whatever it is called.
  - **Variable names can't collide.** `io.github.evil/digitalocean` with an `api_token` got `MCP_DIGITALOCEAN_API_TOKEN`, the recommended DigitalOcean entry's variable, so a user who had set it would send that token to the other server. That tier, its counts and the shared-host list are gone; a registry card is Official or Community.

## 0.11.4 — 2026-09-24

Security fix. A project checkout could make paseo-mcp overwrite another file the user owns, such as `~/.claude/settings.json`, and so run commands through its hooks.

### Fixed
- Every write replaced the file through a temporary file with a fixed name, `<file>.tmp-paseo-mcp`. A repository could commit a symbolic link with that name next to its `.mcp.json`. `writeFileSync` followed the link, `renameSync` moved it into place, and the content, including every other key the repository's `.mcp.json` carried such as `hooks`, landed in the link's target. That happened on Remove from this project or everywhere, which writes every registered project's `.mcp.json`. A committed `.mcp.json` that was itself a link was written through in the same way, and a backup copied its target's content into the checkout.
- All writes now go through one writer (`server/safe-write.ts`):
  - The temporary file has a random name and is created with `O_CREAT | O_EXCL | O_NOFOLLOW`, so nothing planted can catch the write.
  - A target that is a symbolic link is refused, with a message naming it.
  - A backup refuses a linked source and never overwrites an existing file (`COPYFILE_EXCL`).
  - This covers editor configs, project `.mcp.json` files, `~/.claude.json` switches, exports to Downloads and the saved report cache.
- If one of your own editor configs is a symbolic link (a dotfiles setup, say), paseo-mcp now says so and leaves it alone. Before, it replaced the link with a regular file.
- Found by a security review of the upcoming Add from catalogue feature, which would have made adding to a fresh checkout the normal path.

### Tests
216 tests (was 212). `tests/safe-write.test.ts` replays the attack with a real symlink. Against 0.11.3, three of its four tests fail: the target gets rewritten, a linked `.mcp.json` is written through, and a backup copies the target into the checkout.

## 0.11.3 — 2026-09-24

The first MCP panel open after the plugin starts answers at once. It used to wait 6 to 13 seconds while every server was probed; on a daemon with 36 servers the log showed `paseo-mcp.health took 8.2 s` and `paseo-mcp.tools took 13.4 s` after each reload.

### Why it waited
- The host kept its last verdict and tool lists in memory only. After a reload, an update or a daemon restart, `paseo-mcp.health-cached` and `paseo-mcp.tools-cached` answered `report: null`, and the app then called the fresh `paseo-mcp.health` and `paseo-mcp.tools` and waited for a full pass (`cached.report ?? (await callHealth({}))` in `client/health.tsx`, the same in `client/tools.tsx`).
- The 01:50 line in that log (5.9 s, a pause and no reload) was not a cache miss. No `tools took` line came with it, so the tool lists, set in the same process at 01:00, were still cached, and so was health. With a cached verdict the app only calls the fresh RPC on **Refresh**, **Check now**, **Retry**, or after a successful edit or switch (`refreshDefinitions`). Those wait by design. A press right after the pause also joins the background pass that the read had just started. The "last verdict, refreshed in the background" promise held for health. The tools read had no such refresh and waited up to a minute for the timer; it now refreshes the same way.

### Measured (`npm run bench:cold`: sandbox HOME, 36 servers: 26 answer in 400 ms, 4 OAuth, one slow at 4.5 s, one that never answers, 4 stdio)

| | 0.11.2 | 0.11.3 |
| --- | --- | --- |
| First panel read, fresh host: health / tools | 6.2 s / 13.3 s (waits on a full pass) | 3 ms / 3 ms ("checking") |
| Verdict on screen, fresh host: health / tools | 6.2 s / 13.3 s | up to 1 s after the pass ends (read again every second) |
| First panel read after a reload: health / tools | 6.2 s / 13.3 s | 4 ms / 4 ms (saved verdict, "as of HH:MM") |

The bench measured 9.0 s / 15.0 s to the verdict with a 3 s re-read; the release re-reads every second, so the verdict lands at most a second after the pass ends. The panel stays usable the whole time.

### Changes
- The cached reads never wait on a probe (`server/health.ts`, `server/tools.ts`). With no report yet, a report saved by the last run, or one older than the interval, they start a pass in the background and answer `checking: true`. The app then reads every second until there is a current report. Panels show their existing "checking" and "listing" states meanwhile. A pass started this way that fails is not started again from a read for a minute.
- A pass started from a read never starts the login shell for PATH. It waits for the lookup if one is already running (one always is after start-up) and otherwise uses the inherited PATH (`settledSearchPath` in `server/path.ts`). The timer passes and **Refresh** work as before.
- The last health verdicts and tool lists are saved to `$PASEO_HOME/plugin-data/paseo-mcp/cache.json` (`server/report-cache.ts`). The plugin SDK has no data-directory API; Shared Browser keeps its state in `$PASEO_HOME/plugin-data/shared-browser`, so this uses the same place. The file is written atomically, `0600`, once per completed pass, and only while an app is connected. It is read once on start. A corrupt file, one from another version or one of the wrong shape is ignored.
- No URL, query string, header value, env value or command argument is stored. Each server is keyed by its name and a 128-bit SHA-256 prefix of its URL, headers and command. Notes are the redacted ones the panels already show; tool descriptions are server text, already capped. The file does hold what the panels show beside each server: account labels (with the account email), config paths and the stdio command name. It is `0600`, like `~/.claude.json`, which holds all of that and more.
- After a restart the saved health report carries `stale: { reason: "saved before the plugin restarted", asOf }`. Panels show "as of HH:MM (saved before the plugin restarted)" where they said "checked HH:MM". Each saved tool list is marked "as of HH:MM" the way last-good lists already are, with its own sentence in the server pane, and it counts toward the chip until the server answers again. The saved keys carry over the last-good rule: a list is only kept for a definition that has not changed. That rule now compares URL, headers and command, not just the URL.
- The README's Health checks section says all of this.

- The health and tool probes used `fetch`'s `redirect: "follow"`. On a hop to another origin, fetch drops `Authorization` but keeps custom headers such as `X-Api-Key`. ### Tool search (sources read 2026-09-24)
- Claude Code: "Tool search is enabled by default: MCP tools are deferred and discovered on demand. Claude Code disables it when `ANTHROPIC_BASE_URL` points to a non-first-party host" ([MCP docs, Configure tool search](https://code.claude.com/docs/en/mcp#configure-tool-search)). `ENABLE_TOOL_SEARCH` set to `true`, `auto` or `auto:N` overrides that; `false` loads everything up front ([env vars](https://code.claude.com/docs/en/env-vars)).
- `ENABLE_TOOL_SEARCH=auto` is a threshold: Claude Code "loads the tools it would otherwise defer upfront while their definitions total less than 10% of the context window", and `auto:N` sets N% "where `N` is 0-100" ([MCP docs](https://code.claude.com/docs/en/mcp#configure-tool-search)). `auto` and `auto:N` up to 10 count as on; above 10, or outside 0-100, they count as unknown.
- `ENABLE_TOOL_SEARCH` can sit in settings.json's `env` field ([MCP docs](https://code.claude.com/docs/en/mcp#configure-tool-search)), and so can a proxy `ANTHROPIC_BASE_URL`. A settings file's `env` "overwrites the same variable exported in your shell, and when more than one settings file sets a variable, the highest-precedence one applies" ([settings reference, `env`](https://code.claude.com/docs/en/settings-reference#env)); local beats project beats user ([settings precedence](https://code.claude.com/docs/en/settings#settings-precedence)). Paseo's Claude sessions load all three (`CLAUDE_SETTING_SOURCES` in `claude/agent.js`).
- `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1`: "MCP tool search is disabled and all MCP tools load upfront, even when you set `ENABLE_TOOL_SEARCH`" ([env vars](https://code.claude.com/docs/en/env-vars); only managed settings on v2.1.227+ can keep it on). AI Router sets it on every routed Claude session (`ROUTED_CLAUDE_ENV`), so a routed agent is off twice over.
- Google Cloud's Agent Platform models before Claude 4.5 and Microsoft Foundry deployments hosted on Azure load tools up front ([MCP docs](https://code.claude.com/docs/en/mcp#configure-tool-search)). The plugin cannot see the model or the deployment, so those count as unknown.
- Codex defers MCP tools "when `tool_search` and namespaced tools are supported", which depends on the model's `supports_search_tool` ([openai/codex#29486](https://github.com/openai/codex/pull/29486), merged 2026-06-22). The plugin cannot see the model, so Codex counts as unknown. Nothing we found says any other CLI defers tools, so the others count as off.

## 0.8.0 — 2026-09-23

The plugin no longer chugs. Opening an MCP panel used to start `codex mcp list` once per Codex account, per panel, and wait for each one; now nothing waits on a process.

### Why it was slow
- Every read of the Servers section, the workspace panel and each agent's MCP panel ran `codex mcp list --json` once per Codex account (primary plus every AgentLink slot) with `execFileSync`. That command asks each HTTP server over the network whether it uses OAuth, up to 5 s per server, and the synchronous call froze the whole plugin while it ran: health reads, the composer chip, and the `agent.create` hook all queued behind it. Past the daemon's 30 s RPC limit the app retried, which queued more runs. On a daemon this is the `WARNING: failed to clean up stale arg0 temp dirs` line every ~5 s: Codex prints it on every start.
- The workspace panel threw the Codex answers away (it shows Claude sign-in rows only), and the Claude agent panel asked for every account to use one.

### Measured (`npm run bench`: sandbox HOME, 3 Codex accounts, fake `codex` taking 5 s like a real one waiting on an unreachable server)

| | 0.7.0 | 0.8.0 |
| --- | --- | --- |
| Codex runs, panel closed | 0 / min | 0 / min |
| Codex runs, panel open | 12 / min (66 for one open-and-refresh; 332 s to drain) | 3, once, in the background; none after |
| Plugin frozen for (longest event-loop stall, panel open) | 181 s | 13 ms |
| A cheap RPC while the panel loads (median / max) | 66 s / 284 s | 1 ms / 1 ms |
| RPCs past the daemon's 30 s limit, and app retries | 28, 20 | 0, 0 |
| `agent.create` hook while the panel loads | 70.6 s | 1 ms |
| `auth` / `workspace` / `agent-servers` RPC | 15.1 s each | 1 ms (workspace 57 ms cold: one `ps` + `lsof`) |
| Codex warnings in the plugin log | 102 | 0 (one explanation per account) |

### Changes
- Codex sign-in state (`server/codex-auth.ts`, `shared/accounts.ts`): panel reads answer at once from Codex's grant file (`$CODEX_HOME/.credentials.json`, used where there is no keyring) and Codex's last answer. `codex mcp list` runs only in the background, one process at a time, 20 s limit, when the last answer is missing, older than 30 minutes, or the account's `config.toml` or grant file changed, and on Refresh or a finished sign-in. Only a success is cached; a failure keeps the last good answer, is shown with its time and reason, and is retried after 1, 2, 4 … minutes. The workspace panel never starts Codex; an agent panel checks only its own account.
- Fixed: Codex prints `o_auth` for a connected OAuth server; 0.7.0 read that as "unknown", so Codex grants never showed as connected.
- Codex's stderr is captured instead of passed to the plugin log. The arg0 warning is explained once per account with the directory and the fix (something under `$CODEX_HOME/tmp/arg0` is owned by another user, usually root from `docker exec` without `--user`; `chown -R` it once as root).
- Config reads go through an mtime/size/inode-keyed cache (`server/files.ts`): `~/.claude.json` was parsed five or six times per panel refresh. A file caught mid-write keeps its last good parse for 60 s instead of emptying the server list. Credential files (`auth.json`, `.credentials.json`) are read fresh and never cached.
- No blocking calls left on the RPC path: the login-shell PATH lookup, `ps` and `lsof` are async with timeouts, and one process-table snapshot serves every panel for 5 s. The `agent.create` hook finds the git root by walking up to `.git` instead of starting `git`. Calls back into the daemon (config, workspaces, projects) have a 10 s deadline with a plain-English error.
- Health and tool passes (`server/background.ts`) run only while an app is connected (any RPC in the last 15 minutes), back off 1, 2, 4 … minutes after a failure, and probe eight servers at a time instead of all at once. After a pause, the first read answers with the last verdict and refreshes in the background.
- A server that listed its tools before and fails on a later pass keeps its earlier list, marked "as of HH:MM" with the reason, so a blip does not shrink the chip's tool count.
- Panels keep the last good data when a refresh fails, with an "as of HH:MM" pill and a note saying what failed and why, instead of replacing the content with an error. Errors from the daemon are reworded into plain sentences (`shared/errors.ts`), e.g. a 30 s timeout says the plugin is busy and to try again.
- Client polling: health and tool reads back off after failures; the composer chip's settings poll runs only while there is an agent and backs off when the host does not answer; Codex sign-in is re-read every 3 s only while a background check is running. The agent panel's switch list is re-read on every visit as its comment always said (the host turns refetch-on-mount off).
- Every RPC slower than 5 s is logged with its name. Removed the unused `ToolsSection` component.

### Contracts
All additions are optional, so a 0.7 app reads a 0.8 host and the other way round: `paseo-mcp.auth` takes `refresh` and returns `checking`; accounts carry `statusAsOf`, `checking`, `statusNote`; a tool list entry can carry `stale: { reason, asOf }`.

### Tests
102 tests (was 76): Codex state mapping and grant rules (`tests/accounts.test.ts`), the file cache and last-good tool lists (`tests/cache.test.ts`), background Codex checks with caching, invalidation, backoff and single-flight (`tests/codex-auth.test.ts`), pausing and backoff of background passes (`tests/background.test.ts`), and "no spawn loop" against the real handlers with a fake `codex` (`tests/no-spawn.test.ts`).

## 0.5.1 — 2026-09-10

### Fixed: health checks used the wrong protocol and over-reported problems
- HTTP servers were health-checked with a bare `GET`. Streamable-HTTP MCP servers speak JSON-RPC over `POST`, so a correctly working server answers a `GET` with 400 or 405, and an OAuth server answers anything unauthenticated with 401. A 400 was filed as a warning, and a 401 was counted as a problem needing attention, so on one real host 16 of 44 healthy servers were flagged, including every server with a token in its URL query string.
- The probe now sends the same JSON-RPC `initialize` request an MCP client opens a session with (`content-type: application/json`, `accept: application/json, text/event-stream`, the configured headers, the configured URL intact), follows redirects, and keeps the 5 second timeout. Same host, same 44 servers: 2 need attention (one stdio binary not on PATH, one endpoint answering 404), 18 are OAuth servers answering 401 as they should, the rest are healthy.
- Reclassified honestly: a JSON-RPC result is `ok`; 400/405/406 and redirects are `ok` (reachable); 404 and 5xx are `warn`; refused, reset, DNS failure, TLS rejection and timeout are `down`. 401/403 stay `auth-required` but no longer count as needing attention: `healthNeedsAttention` excludes it, so the composer pill, the panel counts, the Issues filter, and the daemon log line (`N servers, M need attention, K OAuth`) treat a sign-in state as informational. The tag reads "OAuth" in a neutral tone. Missing sign-ins are still reported per account on the Accounts tab, which reads each editor's own grant list.
- Health notes are redacted before they are cached, rendered or logged: never the URL, its query string, a query value, a header value, or a JWT-looking run. Several real definitions carry tokens in the URL, and an error message can echo the whole request.
- Classification, redaction and the probe itself live in `shared/health.ts` with the fetch injectable; `tests/health.test.ts` covers 200 JSON-RPC result (plain and SSE-framed), 401, 403, 405, 400, 301/307, 404, 500, timeout, DNS failure, the request shape, and a token-bearing URL never reaching a note. 28 tests.
